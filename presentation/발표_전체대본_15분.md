## 1. 왜 차량용 NPU에서 이 문제가 중요한가 — 1~6페이지 (약 2분 10초)

### 1페이지

안녕하십니까. Aging Aware NPU Remapping을 발표할 박준범입니다.

**저희가 해결하고자 한 문제는 차량용 NPU가 같은 AI 모델을 장기간 반복 실행할 때 특정 core에만 연산이 집중되는 현상입니다.** 고정된 배치를 계속 사용하면 core별 사용 시간 차이가 누적되고, 장기적으로 노화 차이로 이어질 수 있습니다.

저희는 하드웨어를 추가하지 않고 software에서 convolution의 실행 위치를 바꿔 이 부하를 분산하고, 어느 위치로 옮길지도 자동으로 결정하는 방법을 구현했습니다.

### 2페이지

먼저 실제 core 사용량을 측정하고 장기 정확도에 미치는 영향을 계산하겠습니다. 이후 spatial NPU의 동작을 유지하며 core를 옮기는 API와 planner, 최적 배치를 고르는 MILP policy 순서로 설명하겠습니다.

### 3페이지

먼저 왜 차량용인가부터 말씀드리겠습니다.

차량용 반도체는 사용 기간이 길고 반복적인 stress에 노출되며, 작은 고장도 안전 문제로 이어질 수 있습니다. 2020년 Toyota Prius recall에서도 반복적인 고부하 주행으로 특정 IPM transistor에 열 stress가 집중되면서 동력 상실 가능성이 발생했습니다.

NPU 사례는 아니지만, **차량용 반도체에서는 특정 소자에 부하가 계속 집중되는 현상이 중요하다**는 점을 보여줍니다. AEC-Q100에서도 BTI를 장기 신뢰성 항목으로 다룹니다.

### 4페이지

이러한 장기 노화 mechanism 중 저희가 본 것은 NBTI입니다.

Transistor가 오랜 시간 stress를 받으면 threshold voltage가 변하고, switching이 느려지면서 circuit delay가 증가합니다. 아래 식처럼 이 변화는 stress 시간과 duty에 따라 누적됩니다.

**따라서 core 사용량의 불균형이 장기적으로 core별 노화 속도의 차이가 될 수 있습니다.**

### 5페이지

저희가 사용한 BOS Eagle-N A0는 4행 5열, 총 20개의 Tensix compute core를 가지며, core들은 NoC를 통해 data를 주고받습니다.

Operator마다 사용하는 grid 크기는 다르지만, 같은 operator는 같은 위치에서 반복됩니다. 그래서 실제 ResNet-50에서 core별 사용량을 확인했습니다.

### 6페이지

그래서 Eagle-N에서 ResNet-50을 batch 1로 실행해 device profiler로 측정했습니다.

왼쪽은 operator별 참여 core 수입니다. 오른쪽은 profiler의 core별 TRISC-KERNEL 실행 시간을 누적해, 전체 실행 중 실제로 연산한 비율을 나타낸 heatmap입니다.

가장 많이 사용된 core는 89.1%, 가장 적게 사용된 core는 11.3%로 약 7.92배 차이가 났습니다. **즉, 이 문제는 가정에서 시작한 것이 아니라 실제 full-model 실행에서 확인된 불균형입니다.**

## 2. Core 사용량을 장기 정확도와 연결 — 7~12페이지 (약 3분)

### 7페이지

이 부분의 전체 흐름을 먼저 말씀드리겠습니다.

**누적 사용 시간이 늘어나면 NBTI로 delay가 증가하고, delay가 timing margin을 넘으면 bit error가 발생하며, 이것이 신경망 정확도 저하로 이어집니다.**

저희는 이 과정을 `누적 stress 시간에서 delay`, `delay에서 BER`, `BER에서 RRMSE`, `RRMSE에서 Accuracy` 순서로 연결했습니다.

이 페이지는 RRMSE와 Accuracy의 관계입니다. RRMSE는 bit error를 주입했을 때 신경망 output이 정상 output과 얼마나 달라졌는지를 나타냅니다. 값이 커질수록 accuracy가 감소하며, `m`과 `s`는 ResNet-50에 맞춰 구할 parameter입니다.

### 8페이지

Fitting parameter는 error injection으로 구했습니다. ResNet-50 weight에 표의 BER만큼 무작위 bit error를 주입하고, 10,032장의 이미지로 inference했습니다. 각 BER에서 output의 RRMSE와 top-1 accuracy를 함께 측정했습니다.

표의 세 값은 이 실험의 측정값입니다. 이 값으로 RRMSE–Accuracy 관계의 `m`과 `s`를 구했고, BER–RRMSE 관계도 지수 포화 형태로 fitting했습니다.

**따라서 이후에는 BER를 알면 ResNet-50의 Accuracy를 계산할 수 있습니다.** 이제 NBTI delay를 BER와 연결하겠습니다.

### 9페이지

Delay가 증가해도 각 timing path의 margin 안에 있으면 정상 동작합니다.

실제 path별 margin은 공개되지 않았기 때문에, margin이 정규분포를 이룬다고 가정하고 NBTI delay가 margin보다 커질 확률을 계산했습니다.

**Aging으로 늘어난 delay가 허용 margin을 넘어설 확률을 BER로 본 것입니다.** 이 BER가 앞의 error injection 실험과 연결됩니다.

### 10페이지

이제 그 delay 증가량을 core별 누적 stress 시간으로 구합니다.

`S_i(t)`는 core i가 시간 t까지 stress를 받은 누적 시간입니다. Core를 많이 사용할수록 빠르게 증가하며, delay 변화는 이 값의 `n`승에 비례한다고 두었습니다.

공정에 따라 달라지는 `κC`는 알 수 없으므로 기준점 `T0`를 두었습니다. **T0만큼 stress를 받았을 때 delay가 10% 증가한다고 놓고, 이 값으로 공정 상수를 정규화했습니다.** 이 10%는 고장 조건이 아니라 계산을 위한 기준입니다.

### 11페이지

이 페이지는 지금까지의 관계를 하나로 합친 것입니다.

Core별 `S_i(t)`로 delay 증가율을 구하고, margin 초과 확률로 BER를 구한 뒤, 실험으로 만든 BER–RRMSE–Accuracy 관계에 넣습니다.

**입력은 core별 누적 사용 시간이고, 출력은 시간에 따른 ResNet-50 Accuracy입니다.** 이제 두 배치를 비교할 수 있습니다.

### 12페이지

그 결과가 이 그래프입니다.

x축은 경과 시간, y축은 계산된 top-1 accuracy입니다. 빨간색은 고정 배치, 초록색은 부하를 이상적으로 균등 분배한 경우입니다. `T0=20년`, `n=0.2` 등 나머지 조건은 같습니다.

고정 배치보다 균등 배치에서 정확도 감소 시점이 약 2년 늦어졌습니다. 실제 20년 측정값이 아니라 앞의 가정을 이용한 simulation이지만, **core 부하 분산이 정확도 저하 시점을 늦출 수 있음을 보여줍니다.**

그렇다면 실제 Eagle-N에서 core의 실행 위치를 바꿀 수 있는지 살펴보겠습니다.

## 3. Spatial NPU에서 core를 어떻게 옮길 것인가 — 13~24페이지 (약 3분 15초)

### 13페이지

먼저 convolution core remapping을 가능하게 하는 API입니다.

### 14페이지

**저희의 해결 방법은 전부 software level에서 동작합니다.**

TTNN 개발자가 보는 연속된 logical grid는 runtime에서 virtual, NoC coordinate를 거쳐 실제 worker coordinate로 변환됩니다.

저희는 이 변환 단계에서 logical grid의 의미는 유지하고 실제 worker 위치만 바꿨습니다. 따라서 hardware 추가 없이 API와 planner로 remapping할 수 있습니다.

### 15페이지

현재 코드에서는 operator에 따라 `cores_x`와 `cores_y`, 즉 grid 크기는 바뀌지만 시작 coordinate가 `(0,0)`으로 고정되어 있습니다.

서로 다른 크기의 grid를 같은 원점에 놓으면 일부 core가 계속 겹칩니다. **저희가 바꾼 것은 grid 크기가 아니라 고정된 시작 위치입니다.**

### 16페이지

그런데 여기서 단순히 사용량이 적은 core를 골라 연산을 흩어 놓을 수는 없습니다.

Eagle-N은 연산과 data가 core grid 위에 배치되는 spatial NPU입니다. 하나의 sender가 전체에 data를 보내기도 하고, activation은 row, weight는 column 방향으로 동시에 multicast하기도 합니다.

**따라서 core 위치를 바꾸려면 그 위에서 실행되는 sharding과 data movement의 공간적 구조를 함께 유지해야 합니다.**

### 17페이지

그 제약이 가장 직접적으로 보이는 것이 multicast API입니다.

수신 영역은 시작점과 끝점으로 지정되므로 한 번의 multicast 명령은 사각형만 표현합니다. 중간에 빠진 core가 있으면 여러 사각형으로 나누어 보내야 합니다.

### 18페이지

Height sharding에서는 activation의 height 방향 data가 core 순서대로 나뉘고, weight와 activation을 필요한 core에 multicast합니다.

여기서 중요한 것은 세부 명령이 아니라 **core의 순서가 곧 data shard의 순서라는 점**입니다.

### 19페이지

Block sharding은 height와 channel을 2차원 grid에 나누므로 activation은 row, weight는 column 방향으로 전달됩니다.

즉 block sharding에서는 row와 column의 구조를 깨뜨리면 기존 data movement도 함께 깨집니다.

### 20페이지

Width sharding도 logical core 순서에 따라 channel shard와 multicast 대상이 정해집니다.

세 sharding 방식의 data 이동은 서로 다르지만, **모두 연속된 logical core grid를 기준으로 동작한다는 공통점**이 있습니다.

### 21페이지

Height와 block sharding에서는 경계에 필요한 halo data를 인접 shard끼리 교환하므로 이웃 관계도 유지해야 합니다.

그래서 remapping 이후에도 logical core의 row, column 순서와 인접 관계가 바뀌지 않아야 합니다.

### 22페이지

이 조건을 만족하도록 저희가 허용한 placement가 이 그림입니다.

기존 배치는 하나의 사각형이고, row 또는 column을 건너뛰면 두 개, 두 축을 모두 건너뛰면 최대 네 개로 나뉩니다.

이때 주황색 core의 logical 순서는 유지됩니다. **즉 core를 무작위로 흩어 놓는 것이 아니라, 사각형 기반 data movement를 유지하면서 위치만 바꿉니다.**

### 23페이지

이를 실제 core remapping API로 구현했습니다.

### 24페이지

개발자가 제외할 worker row와 column을 지정하면 API가 하나, 둘 또는 네 개의 multicast 사각형을 생성합니다.

이제 특정 core를 건너뛸 수 있지만, 사각형이 나뉘면 data를 여러 번 보내야 합니다.

**그래서 다음 질문은, core를 옮기는 비용보다 사각형을 나누는 비용이 얼마나 큰가입니다.**

## 4. Remapping의 비용과 software 적용 방식 — 25~32페이지 (약 2분 30초)

### 25페이지

먼저 sender의 위치가 latency에 영향을 주는지 측정했습니다.

4행 5열 grid에서 동일한 multicast의 sender를 20개 위치로 옮기고, profiler로 receiver wait cycle의 중앙값을 측정했습니다. 파란색은 NoC0, 주황색은 NoC1입니다.

위치를 전체 grid에 걸쳐 바꿔도 차이는 약 2%였습니다. **즉 어느 core에서 보내는가는 remapping의 주요 비용이 아니었습니다.**

### 26페이지

다음은 대상 core 수를 바꿨습니다. x축은 사각형의 core 수, y축은 완료 cycle입니다. 9개에서 20개로 늘려도 latency 증가는 약 4.4에서 5.0%였습니다.

Core 수의 영향은 있었지만 증가 폭은 크지 않았습니다.

### 27페이지

반면 하나의 grid를 여러 사각형으로 나누면 차이가 커졌습니다.

같은 4행 5열 grid에서 바깥쪽 row나 column을 제외하면 한 사각형, 가운데를 제외하면 두 사각형이 됩니다. 동일 전송을 반복했고, 막대는 평균, error bar는 최소와 최대입니다.

두 사각형으로 나뉜 경우에는 한 사각형인 경우보다 sender latency가 최대 약 170 cycle 증가했습니다. **Remapping 비용을 결정하는 핵심은 sender 위치나 core 수보다, placement가 몇 개의 사각형으로 분리되는가였습니다.**

### 28페이지

그 이유는 실제 multicast 과정에 있습니다.

한 사각형에는 data multicast와 semaphore multicast가 각각 필요합니다. Write barrier는 공유하지만, 이 두 작업은 사각형 수만큼 반복됩니다.

따라서 placement를 지나치게 나누면 overhead가 커집니다. 이를 policy의 segment 제한에 반영했습니다.

### 29페이지

다음은 이 기능을 기존 TTNN 코드에 적용하기 위한 remapping planner입니다.

### 30페이지

Remapping을 위해 모든 TTNN 연산 코드를 physical core 배치에 맞춰 다시 작성하는 것은 현실적이지 않습니다.

그래서 logical grid와 실제 worker 배치 사이에 planner를 뒀습니다. 개발자는 기존의 연속된 grid만 사용하고, planner가 logical row와 column을 실제 worker coordinate로 변환합니다.

**개발자는 연속된 logical grid만 보고, 실제 worker 배치는 planner가 처리합니다.** 이 과정에서도 logical shard의 순서는 그대로 유지됩니다.

### 31페이지

Planner는 다음 연산에서도 현재 placement를 유지할 수 있는지 판단합니다.

다음 convolution이 호환되면 remapped placement를 전달하고, 호환되지 않으면 default placement로 돌아갑니다.

따라서 각 연산 개발자가 remapping 상태를 직접 관리할 필요가 없습니다.

### 32페이지

여기서 API와 policy의 역할을 구분할 수 있습니다.

**API와 planner는 remapping을 가능하게 하는 mechanism을 제공합니다. 그리고 이 mechanism을 언제, 어디에, 어떤 형태로 적용할지는 policy가 결정합니다.**

Policy는 core 부하와 multicast 분할 비용, 연산 사이의 placement 변경을 함께 고려합니다. 저희는 이를 자동 계산하는 software framework를 만들었습니다.

그리고 저희가 풀어야 하는 이 최적화 문제는 MILP의 형태와 정확히 맞습니다.

## 5. 최적의 remapping을 자동으로 결정 — 33~40페이지 (약 3분 20초)

### 33페이지

MILP를 이용한 placement policy입니다.

### 34페이지

**저희의 최적화 문제는 곧 MILP입니다.**

각 convolution에는 placement 후보가 있고, 어느 후보를 사용할지는 정수 선택입니다. 반면 선택된 placement가 각 core에 더하는 실행 시간은 선형으로 합산됩니다.

이 구조가 Mixed-Integer Linear Programming과 정확히 맞습니다. 가능한 placement와 제약을 넣으면 solver가 core 부하를 가장 잘 분산하는 조합을 찾습니다.

### 35페이지

이 식은 worker `c`의 누적 TRISC cycle입니다. `H B_c`는 remapping하지 않는 operation의 고정 부하이고, 두 번째 항은 remapping 대상의 부하입니다.

`A_dpc`는 operation `d`를 placement `p`에 놓을 때 worker c에 배정되는 cycle입니다. Profiler로 측정한 core별 cycle을 후보 위치에 옮겨 미리 계산하므로 고정값입니다.

Solver는 `n_dp`, 즉 20번의 inference 동안 각 placement를 몇 번 쓸지를 정합니다. **고정 부하는 두고, 옮길 수 있는 convolution의 배치만 조절해 가장 바쁜 core를 낮춥니다.**

### 36페이지

목적은 세 단계의 우선순위로 정했습니다.

첫째, 가장 많이 사용되는 core의 부하를 줄입니다. Aging은 평균보다 가장 빨리 stress가 누적되는 core가 중요하기 때문입니다.

둘째, 그 최적값을 유지하며 전체 부하를 고르게 합니다. 셋째, 앞의 결과를 유지하며 placement 종류를 줄입니다.

즉 **최악의 core를 먼저 줄이고, 그다음 전체를 고르게 만들며, 성능이 같다면 더 단순한 policy를 선택합니다.**

### 37페이지

이 그래프는 허용 segment 수에 따른 MILP 결과입니다. 직접 측정한 막대가 아니라, profiler 측정값을 입력으로 사용한 optimization 결과입니다.

한 segment는 13.3%, 최대 두 segment는 26.5%를 줄입니다. 네 segment도 26.5%로 추가 이득이 거의 없습니다. 점선 31%는 완전 균등 분배의 이론적 한계입니다.

**두 개의 사각형만으로 가능한 개선의 대부분을 얻고, 네 개로 나눌 때의 추가 multicast 비용은 피할 수 있습니다.** 그래서 최종 policy는 최대 두 segment를 사용했습니다.

### 38페이지

그 policy를 적용했을 때 예측되는 core별 부하입니다.

x축은 worker coordinate, y축은 각 worker가 담당한 TRISC cycle 비율입니다. 주황색은 stock profile 측정값, 파란색은 MILP placement를 적용한 계산값이며, 점선 5%는 완전 균등 상태입니다.

총 연산량은 그대로 유지하면서, 가장 높은 core의 비율이 7.25%에서 5.33%로 감소했습니다. **즉 가장 많이 일하던 core의 누적 부하를 26.49% 줄였습니다.**

### 39페이지

마지막으로 실제 hardware에서 remapping이 latency를 늘리지 않는지 확인했습니다.

동일한 ResNet-50을 stock으로 한 번, layer 1과 2에 remapping을 적용해 한 번 실행하고, 각 run의 TRISC-KERNEL 시간을 같은 방식으로 합산했습니다.

Stock은 2.057ms, remapping은 2.049ms로 차이는 0.35%, 약 7.2마이크로초였습니다. 성능 향상이 아니라, **현재 검증 범위에서 측정 가능한 latency overhead가 없었다**고 해석했습니다.

### 40페이지

이제 측정한 부하 감소를 앞의 reliability model에 다시 넣었습니다.

왼쪽의 빨간색은 기존 배치, 파란색은 MILP policy, 초록색은 완전 균등 분배입니다. 같은 조건의 simulation에서 MILP policy는 정확도 감소 시점을 약 1.5년 늦췄습니다.

오른쪽 1.35배는 가장 많이 사용되는 core가 같은 누적 busy time에 도달하는 시간의 비율입니다. Peak가 7.25%에서 5.33%로 줄어 약 1.35배가 됩니다.

**정리하면, 실제 측정으로 확인한 결과는 peak core 부하의 26.49% 감소와 latency overhead가 없었다는 점입니다. 그리고 이 부하 감소를 reliability model로 환산했을 때 약 1.5년, 1.35배의 개선이 예측됐습니다.**
