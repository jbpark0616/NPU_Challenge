# 시간축 NoC 데이터 추출 지시서

Eagle-N A0 (Tensix 20 compute cores, 5×6 grid) 에서 ResNet-50 실행 시
**"언제 얼마나 관측 여유가 있는가"** 를 정량화하기 위한 시간축 데이터 추출 및 시각화.

기존에 op별 공간 분포(link/NIU demand)는 확보됨. 이번 작업은 **시간 차원 추가**.

---

## 0. 배경 / 이 데이터로 답하려는 질문

여유 코어를 오류 검출(observer)에 쓰려고 한다. 판단에 필요한 것:

1. **언제** NoC에 여유가 있는가 (기회적 스케줄링 가능 여부)
2. 뜨거운 링크가 **고정인가 이동하는가** (정적 배치 vs 동적 재배치)
3. **최악 구간**에서도 남는 최소 예산은 얼마인가 (보수적 설계 하한)
4. 유휴 코어 수와 NoC 여유가 **동시에** 존재하는 구간이 있는가

## 1. 필수 전제 확인 (작업 시작 전)

### 1.1 op 시간 겹침 여부
Tracy 타임라인에서 op 간 `t_start` / `t_end` 가 겹치는지 먼저 확인할 것.

- **겹치지 않음 (순차)** → op별 bytes ÷ op duration = 그 구간의 rate. 단순.
- **겹침 (파이프라인)** → op별 rate를 단순 이어붙이면 **순간 peak를 과소평가**함.
  반드시 공통 시간 그리드에 리샘플 후 **동시 수요를 합산**해야 함.

이 확인 결과를 먼저 보고할 것. 결과에 따라 이후 처리가 달라짐.

### 1.2 좌표 신뢰도 구분 (중요)
논리 좌표는 물리 배치와 1:1 대응이 아님 (harvesting, DRAM/IO 행·열 삽입).

| 트래픽 종류 | 링크 귀속 신뢰도 | 처리 |
|---|---|---|
| compute ↔ compute | 높음 | **주 분석 대상** |
| compute ↔ y=3 sink (DRAM) | 낮음 | boundary로 분류, caveat |
| y=3 ↔ y=3 | 낮음 | boundary |
| x=5 관련 wrap | 낮음 | boundary |

→ **모든 산출물은 `real_ops` (compute↔compute만) 와 `real_boundary` (전체) 두 버전으로 생성.**
→ 주 결과는 `real_ops`, `real_boundary` 는 참고용.

## 2. 추출할 데이터

### 2.1 op 단위 테이블 → `ops.csv`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `op_id` | str | 예: `op235_stage4_rhid31744_Matmul` |
| `op_type` | str | Conv2d / Matmul / Eltwise / ... |
| `stage` | str | ResNet stage |
| `t_start_us` | float | 시작 시각 (μs) |
| `t_end_us` | float | 종료 시각 (μs) |
| `duration_us` | float | `t_end - t_start` |
| `n_active_cores` | int | 이 op에서 일한 compute 코어 수 (0~20) |
| `active_cores` | str | `"(0,0);(0,1);..."` 형태 |
| `noc0_bytes_real` | int | compute↔compute만 |
| `noc1_bytes_real` | int | 〃 |
| `noc0_bytes_total` | int | boundary 포함 |
| `noc1_bytes_total` | int | 〃 |
| `noc0_rate_real` | float | `noc0_bytes_real / duration_us` (B/μs) |
| `noc1_rate_real` | float | 〃 |

### 2.2 링크 단위 시계열 → `link_timeseries.csv`

공통 시간 그리드로 리샘플. **bin 크기는 최단 op duration의 1/10 또는 1μs 중 작은 값**.

| 컬럼 | 설명 |
|---|---|
| `t_us` | bin 시작 시각 |
| `noc` | 0 / 1 |
| `link_id` | `"(sy,sx)->(dy,dx)"` |
| `bytes_per_us` | 해당 bin에서의 rate |
| `traffic_class` | `real` / `boundary` |

op이 겹치면 같은 (t_us, noc, link_id) 에 대해 **합산**.

### 2.3 NIU 단위 시계열 → `niu_timeseries.csv`

| 컬럼 | 설명 |
|---|---|
| `t_us` | bin 시작 시각 |
| `noc` | 0 / 1 |
| `core` | `"(row,col)"` |
| `src_bytes_per_us` | 주입 |
| `sink_bytes_per_us` | 흡수 |
| `traffic_class` | `real` / `boundary` |

> NIU는 링크와 별개의 병목이 될 수 있으므로 반드시 분리 기록.

### 2.4 시간 그리드 요약 → `timeline.csv`

| 컬럼 | 설명 |
|---|---|
| `t_us` | bin 시작 시각 |
| `noc0_total_rate` | 전체 NOC0 rate (B/μs) |
| `noc1_total_rate` | 전체 NOC1 rate |
| `noc0_max_link_rate` | 그 시점 NOC0에서 가장 뜨거운 링크의 rate |
| `noc1_max_link_rate` | 〃 |
| `n_active_cores` | 활성 compute 코어 수 |
| `n_idle_cores` | `20 - n_active_cores` |
| `active_op_ids` | 그 시점 실행 중인 op 목록 |

## 3. 시각화

### 3.1 [최우선] 다중 패널 타임라인 → `fig_timeline.png`

**공유 x축 = 실제 시간(μs). op 인덱스 금지.**
op 폭이 지속시간에 비례해야 버스트 구조가 보임.

```
패널 1 (높이 3) │ NoC 수요 (B/μs)
                │   선 2개: NOC0(파랑), NOC1(빨강)
                │   real 은 실선, boundary 포함은 점선
                │
패널 2 (높이 2) │ 최대 링크 rate (B/μs)
                │   NOC0 / NOC1 각각
                │   → 총량이 아니라 "가장 막힌 링크" 관점
                │
패널 3 (높이 2) │ 활성 코어 수 (0~20), step plot
                │   유휴 구간을 회색 음영으로 강조
                │
패널 4 (높이 1) │ op 구간 밴드 (op_type 별 색상)
                └────────────────────────────→ t (μs)
```

- 모든 패널 `sharex=True`
- 패널 1에 **NOC0 선이 거의 0에 붙어 있는 것이 핵심 메시지** → 눈에 띄게
- 여백 최소화, 범례는 각 패널 우상단

### 3.2 [중요] 링크 × 시간 히트맵 → `fig_link_heatmap.png`

- x = 시간(μs), y = link_id, color = `bytes_per_us` (log scale)
- **y축은 총 부하 내림차순 정렬** (뜨거운 링크가 위)
- NOC0 / NOC1 을 **상하 2개 subplot**, 컬러스케일 공유
- 목적: **뜨거운 링크가 시간에 따라 이동하는지 확인**
  - 가로줄이 계속 진함 → 고정 hotspot → 정적 배치 가능
  - 진한 구간이 y축을 오르내림 → 이동 → 동적 재배치 필요

이 그림의 해석을 텍스트로 함께 보고할 것.

### 3.3 CDF → `fig_cdf.png`

- x = NoC rate (또는 최대 링크 rate), y = 누적 시간 비율
- NOC0 / NOC1 각각 곡선
- 목적: **"부하가 X 이하인 시간이 전체의 Y%"** 문장을 쓰기 위함
- 참고선: 50%, 80%, 95% 시간 지점에 수평선 + 값 주석

### 3.4 op 산점도 → `fig_op_scatter.png`

- x = `duration_us` (log), y = `noc1_bytes_real` (log)
- 점 색 = `op_type`, 점 크기 = `n_active_cores`
- 대각선 등고선으로 동일 rate 선 표시
- 목적: 어떤 op이 버스트인지, matmul이 어디 몰리는지

## 4. 파생 지표 (텍스트로 보고)

계산해서 요약 리포트 `summary.md` 에 기록:

1. **NOC0 / NOC1 총 바이트 비** (real 기준) — "NOC0는 전체의 N%"

5. **최대 링크 rate의 p50 / p95 / max** (NOC0, NOC1 각각)
6. **op별 바이트 상위 10개** — 어떤 op이 트래픽을 지배하는가
7. **op 겹침 여부와 최대 동시 실행 op 수**

## 0. [선행] max link rate 정밀도 수정

### 문제
`summary.md` 에 자기모순이 있음:

- NOC0 는 전체 바이트의 **20%** 를 나름
- NOC0 완전 유휴는 **56.9%** of run
- 그런데 `NOC0 max link: p50 = 0, p95 = 0`

→ 유휴가 56.9% 인데 max link 가 95% 구간에서 0 이라는 건 모순.
**약 38% 구간에서 "트래픽은 있는데 최대 링크 rate 가 0"** 으로 계산되고 있음.

### 원인 추정
NOC0 트래픽이 다수 링크에 얇게 분산 → 링크당 rate 가 1 B/μs 미만 → **정수 반올림으로 0**.

### 조치
1. `bytes_per_us` 를 **float64 로 유지**. 어디서 `int` 캐스팅/반올림이 일어나는지 추적해 제거.
2. 재계산 후 `summary.md` §5 표를 소수점 3자리까지 다시 출력.
3. 검증: `NOC0 max link == 0` 인 시간 비율이 `NOC0 total rate == 0` 인 비율(56.9%)과 **일치해야 함**. 일치하지 않으면 아직 문제가 남은 것.
4. 결과를 보고할 것. 값이 작지만 0 이 아니면, `summary.md` 의 서술을
   *"NOC0 는 링크당 부하가 무시 가능한 수준"* 으로 정정 (현재의 *"0"* 은 부정확).

## 1. `fig_op_scatter.png` — 축 범위 (효과 대비 가장 쉬움)

### 문제
- x 축: `10⁻¹ ~ 10³` 인데 실제 데이터는 `10⁰ ~ 3×10²`
- y 축: `10² ~ 10⁹` 인데 실제 데이터는 `10⁴ ~ 5×10⁶`
- **플롯 면적의 약 70% 가 빈 공간.** 점들이 중앙에 뭉쳐 op_type 별 분포가 안 읽힘

### 조치
```python
ax.set_xlim(x.min() * 0.7, x.max() * 1.4)
ax.set_ylim(y.min() * 0.7, y.max() * 1.4)
```

### 추가
- `size = n_active_cores` 가 시각적으로 구분이 안 됨. 다음 중 택1:
  - (a) 크기 범위를 벌린다: `s = 20 + (n/20)**2 * 400`
  - (b) 크기를 버리고 **마커 테두리 색**으로 인코딩
  - (c) 아예 제거하고 색(op_type)만 사용 ← 가장 깔끔, 권장
- 등rate 대각선(1 kB/μs 등) 라벨은 유지. 좋음.

## 2. `fig_cdf.png` — x 축 로그 + 기준선 위치

### 문제
- 왼쪽 패널 x 축이 175,000 까지 가는데 데이터의 95% 가 25,000 이하 → 곡선의 유의미한 부분이 왼쪽 끝에 압축됨
- 50 / 80 / 95% 기준선 라벨이 오른쪽 여백에 떠 있어 어느 선인지 대응이 안 됨

### 조치
1. **x 축 `log` scale** 로 변경 (양 패널 모두).
   - log 로 0 을 못 그리므로 `symlog` 사용하거나 `x + 1` 로 시프트
   - 대안: p99 까지만 표시하고 `"max = 175,000 (off-scale)"` 을 텍스트로 주석
2. 기준선 라벨을 **선 위에 직접** 올리기:
   ```python
   ax.axhline(0.95, ls='--', lw=0.8, c='gray')
   ax.text(ax.get_xlim()[0], 0.95, ' 95%', va='bottom', ha='left', fontsize=8, color='gray')
   ```
3. **0번 수정 후 재생성할 것.** NOC0 곡선이 x=0 에서 0.95 로 수직 점프하는 건 정밀도 문제의 결과임.

## 6. 별도 후속 분석 (그림 작업과 무관, 잊지 말 것)

### 6.1 배치 크기 및 유효 활용률
- 이 실행의 **batch size** 확인
- ResNet-50 추론 연산량(약 8 GOPs @ batch 1) 대비 **실측 4099.9 μs** 의 유효 활용률 계산
- 64 TOPS 기준 이론 하한과 비교 → peak 대비 몇 % 인지
- `4099.9 μs` 가 시뮬레이션 device-time 인지 실측 wall-clock 인지 명시

### 6.2 패딩 오버헤드 해석적 계산 (하드웨어 불필요)
op 별로, 텐서 shape 만으로:

- 출력 텐서를 N개 코어에 분할했을 때 32×32 타일 입도에 맞추기 위한 **패딩 비율**
- N = 1, 2, 4, 8, 12, 14, 16, 20 각각에 대해 계산
- 지표: `유효 원소 / (유효 + 패딩)`
- **출력**: op × N 의 효율 표 + "효율이 꺾이는 N\*" 를 op 별로 표기

> 목적: 현재 평균 활성 코어 14.5 가 **최적이라서 그런지, 단순히 그렇게 코딩돼서 그런지**를 판별.
> 이것이 연구의 핵심 전제이므로 우선순위 높음.
